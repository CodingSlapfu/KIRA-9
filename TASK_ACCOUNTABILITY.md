# KIRA-9 — Mandatory no-missed-task development standard (2026-11-05)

## Why this exists
AQUORA v0.6.5 had a successful **limited hotfix** acceptance (issues #2,#16,#24,#26–#30) while its deferred **second visualizer redesign #17** remained unimplemented. Its root active queue simultaneously reported no v0.6.5 outstanding tasks; all 30 GitHub issues still showed open despite some software being complete. **Never make the same scope mistake in KIRA-9.**

## Required lifecycle (Work Mode)
1. **Before implementation:** Gather the latest owner requirements and revisions from this handoff, any later chat/attachments, GitHub issues and latest comments. Treat the newest explicit owner's intent as authoritative; record changed/superseded requirements rather than silently dropping the old one. Read one concise start-here and one active queue, not repeated archives.
2. Assign **one canonical ID** per granular requirement in `requirements/manifest.json`. The frozen original ID set is `requirements/required_ids.txt`; new owner requirements get new IDs and provenance, not renamed aliases. Map every open/closed issue and relevant latest owner comment to at least one ID. If an item is already proven complete, record its commit/test/artifact evidence; don't rebuild it.
3. Create a **source-to-test-to-artifact acceptance row** for each requirement: owner wording/link, status, implementation location, verified GitHub source commit, targeted test references, demonstration artifact, and physical-hardware responsibility. Labels: `new`, `partial`, `blocked`, `software_completed`. Use separate `hardware_status=owner_unverified` (do not treat this as a code failure).
4. After each milestone, update only affected rows and tests. Mark software completed only after real source changes, meaningful unit/host/device/emulator tests, **visual/audio proof where relevant**, reproducible native build and correct release linkage. A renamed menu, a screenshot mock, passing compile, or an old hotfix claim is not completion of a subjective design requirement.
5. At a user-approved deferral, preserve a visible active-queue line including release target, explicit approval and newest owner comment. **A scoped hotfix cannot set the entire product backlog to empty.** No P0 issue silently disappears at publication. Differing version intent does not grant implicit approval to defer.
6. Before publication, independently compare owner intent → design reference/previews → implemented source → executed tests → resulting firmware/web artifacts. Visual design acceptance must include real **240×240 animated frame sequences**, physical mechanisms that visibly move, synchronized actual phonemes, multiple expressions and rare body glitches without screen effects; no proxy screenshot/hash alone. Vocal acceptance needs actual intelligible English recordings and style comparisons, not just nonzero PCM.
7. Run `python3 tools/requirement_gate.py --phase plan` before working, and `python3 tools/requirement_gate.py --phase release` before publishing. The latter intentionally fails until every mandatory first-release requirement has source/test/artifact evidence and the owner comment audit is current. Run `python3 tools/test_requirement_gate.py` as a negative regression that proves omitted requirements cause failure. Add this release gate to CI. It enforces traceability but **cannot independently authenticate** the truth of links or fetch new GitHub comments: Work Mode must actually verify evidence.
8. After a release, move proven completed items to dated `CHANGELOG.md`/`validation/`, leave **only outstanding/partial/owner-hardware-unverified** in `NEXT_BUILD_ACTIVE.md`, update issue status, and keep a permanent versioned register rather than erasing records. Verify remote GitHub backup+release URLs and checksums and publish site only after all software gates.
9. Development time law: exclusive writer/publisher lock; checkpoint with verified remote SHA at start, milestones, before long compilation and on interruption; no concurrent builds; reuse existing test results when inputs unchanged; batch work; no repeated `proceed` questions; resume newest verified state rather than rebooting from scratch. Record exact blocker and one-step resume command on interruption.
